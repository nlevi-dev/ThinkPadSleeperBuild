# CS5211: execution experiments, 2026-09-28

Follow-up: [the five-stage investigation](cs5211-deep-investigation-2026-09-28.md)
adds coverage and an executable reconstruction. It also corrects the blanket
exclusion of profile byte 0: its seven upper bits preserve the stock nonzero
clock branch and remain secondary colour-setting candidates.

## Outcome

Executed **2,267 experiments** against the original firmware with an independent
8051 instruction/timer emulator. Separately checked 21 cases with uCsim, including
the baseline boot and every arithmetic discrepancy against a host float model.
The two CPU emulators agreed on every compared register value.

New results materially narrow the search:

- The large arithmetic routine is a **clock-configuration calculation**, strongly
  consistent with DisplayPort Mvid/Nvid recovery. It is not an observed RGB LUT
  calculation. Profile byte 0 also controls its divider branch.
- Physical ROM `1113–111a` controls startup/shutdown delays. `1112` controls
  brightness mode, power-button polling, and brightness-button direction.
- Link recovery **reapplies profile registers**. A temporary register experiment
  can be undone by a subsequent link fault. The GPIO profile selection is latched
  at startup, not reread during ordinary recovery.
- Invalid clock inputs can reach the normal firmware loop. Boot completion alone
  is an inadequate test oracle.
- **The exact JEIDA/SPWG and 18/24-bit hardware fields remain unidentified.**
  Execution reveals what reaches the registers, not how the serializer interprets
  undocumented bits. No panel colour result has been measured here.

All addresses below are hexadecimal. ROM addresses are physical EEPROM offsets;
PCs are logical 8051 CODE addresses, corresponding to physical ROM `1000 + PC`.

## Method and limits

Original 8,192-byte ROM SHA-256:
`a7a5b681eb62026afcb11232635fb68251f40ca0348f6b513913bc51bb4a2451`.

Primary CPU core: [jarikomppa/emu8051](https://github.com/jarikomppa/emu8051),
commit `5dc681275151c4a5d7b85ec9ff4ceb1b25abd5a8`. Its instruction implementations
were not modified. `scripts/cs5211_emulator.c` wraps instructions and XDATA access
to record executed PCs, MOVC data reads, register reads/writes, and exceptions.
The wrapper's resume logic requires the breakpoint instruction to execute before
stopping there again, including when an interrupt intervenes.

Independent check: SDCC 4.6.0 / **uCsim 0.9.9**, installed locally as `s51`.
Both execute the original instructions. Host float arithmetic is a third,
approximate reference, not a replacement for firmware execution.

The CS5211 peripherals are **not emulated**. XDATA is byte storage with explicit
synthetic input values. Peripheral writes do not cause electrical effects,
status transitions, DP negotiation, or pixel conversion. Unseeded reads return
zero and are reported. Baseline unseeded reads are `0006, 001f, 00aa, 00e1,
0554, 0613`. Custom chip SFR behaviour, watchdogs, the EEPROM boot loader,
and actual oscillator timing are outside the model.

Baseline seeds include `00ca=00`, `000c=21`, `0611=77`, `060b=02`, `060a=0a`,
`01b4=5c`, and two big-endian 24-bit values of 2 and 5 at `0549` and `054c`.
These are chosen inputs, **not a captured hardware trace**. The seeded status
bytes select the successful link branch.

The CPU model loads ROM `1000–1fff` into CODE `0000–0fff`. Consequently it cannot
test the hardware's possible use of EDID or the opaque `0800–0983` area. Changing
those bytes and observing no CPU difference would not rule out a gamma table.
The three identical 128-byte nibble-valued blocks remain unexplained.

## 1. Clock calculation and profile byte 0

Routine PC `0a20–0c47` consumes:

```text
M = BE24(XDATA[0549:054c])
N = BE24(XDATA[054c:054f])
R = XDATA[060a]
P = floor(((27 * R * M) modulo 2^32) / N)    [N > 0]
Q ≈ 458752 * R * M / N
```

Q is calculated through the ROM's software floating-point helpers and converted
to an integer; its low 24 bits are written, most significant byte first, to
`0564–0566`. P selects the following register outputs:

| P interval | `00e7` | `00e1[5:4]`, profile[0] = 0 | `00e1[5:4]`, profile[0] != 0 |
| --- | ---: | ---: | ---: |
| Below 25 | `08` | 3 | 3 |
| 25–49 | `04` | 2 | 3 |
| 50–99 | `02` | 1 | 2 |
| 100 and above | `00` | 0 | 1 |

The routine also clears `00e1` bit 6, preserves unrelated bits, sets `0554[7:6]`,
pulses `0006` bit 3, and writes `00d0=ff`. Later startup sets `00e1` bit 7.

With M=2, N=5, R=10, P=108 and Q=`1c0000`. R=6 and R=10 match the standard
DP rate codes for 1.62 and 2.7 Gbit/s; multiplying by 27 yields 162 and 270 MHz
symbol rates. This plus the ratio arithmetic strongly supports interpreting P
as pixel MHz and these inputs as Mvid/Nvid. The standard rate codes and lane
status flags are independently documented in the
[Linux DP definitions](https://github.com/torvalds/linux/blob/master/include/drm/display/drm_dp.h).
The correspondence to these specific CS5211 XDATA addresses is inferred.

Profile[0] is also copied in full to `009f`. The stock value is 1. Clearing it
changes both `009f` and clock-divider selection. A single/dual-pixel control is
plausible; its exact hardware encoding remains unproved. **Do not interpret a
profile[0] colour change as evidence of a JEIDA switch without checking timing.**

The 512 seeded valid-range fuzz cases all matched the integer divider model.
Fifteen Q values differed from native float32 evaluation by exactly ±1.
uCsim independently reproduced all fifteen firmware values. Thus a convenient
host float32 expression is not a byte-exact substitute for the ROM helpers.
No claim is made that this one-count difference explains the colour fault.

### Invalid inputs

- M=0 or rate=0 produces Q=0 and the lowest-rate divider selection.
- N=0, including M=N=0, produces Q=`ffffff`, yet execution continues to the
  ordinary link loop with the synthetic ready status still asserted.
- M=N=`ffffff`, R=10 overflows the 32-bit P numerator: the divider decision
  differs from the unbounded 270 MHz calculation. This example is outside the
  normal advertised video clock range; it is a fault test, not a proposed cause.

## 2. What the profile mutations actually change

Full-boot execution confirmed the earlier copy-slice map:

| Profile byte | Register | Processing |
| ---: | --- | --- |
| 0 | `009f` | Full byte; also zero/nonzero clock branch above |
| 1 | `01dc` | Full byte |
| 2 | `01de` | Full byte |
| 3 | `01e1` | Bit 3 cleared |
| 4 | `01e2` | Bit 3 set |
| 5 | `01e3` | Full byte |
| 6 | `01e4` | Full byte |
| 7 | `01e7` | Full byte |
| 8 | `01ed` | Full byte |
| 9 | `01f2` | Full byte |
| 10 | `01f3` | Full byte |
| 11 | `01f4` | Full byte OR `((ROM[1122] & 15) << 4)` |
| 12–15 | None observed | Not read on the tested boot path |

Of 128 single-bit profile changes, **34 have identical observed boot effects**:
the two forced bits and 32 bits in the unused tail. The remaining 94 change a
register. Apart from profile[0] becoming zero, they do not alter the tested
firmware control flow. This limits software-only inference: a hardware mapping
bit could look just like a voltage, swapping, dithering, or reserved bit here.

Global `1122[3:0]` overlaps profile[11]'s upper four output bits; those are not
four independent hardware controls. A set global bit can prevent a profile
mutation from clearing its corresponding register bit.

## 3. Brightness and power controls

`ROM[1112] & 3`:

- 0: fixed selected level; intermediate levels run the Timer 0 duty-cycle ISR.
- 1: enables brightness buttons as well as Timer 0.
- 2: writes `00b3=2f`, without the software PWM timer. Consistent with the
  documented bypass mode, although the physical pin behaviour is unmodelled.
- 3: behaved like 0 in the tested cases; it is not established as a supported UI mode.

With mode 1 and initial level 5, three polls of `00b0=20` yield levels 6,7,8;
`00b0=40` yields 4,3,2. `00b0=60` holds the level. Setting `1112` bit 5 swaps
these directions. Active-low input bits 6 and 5 are therefore established as
the firmware's up/down controls, conditional on this mode.

`1112` bit 4 enables a separate power-button routine reading `00b1` bit 5.
A high-to-low input transition changes `01d8` from `bc` to `80`; holding low
does not toggle again. Release and press again restores `bc`.

Physical `111b` provides the initial level; values above 10 select a fallback
level of 10 and fallback limits. `111c/111d` provide lower/upper button limits
when the initial level is accepted. **The limits themselves are not validated
to 0–10 by the shown initialization code**; arbitrary mutations should not be
treated as valid brightness configurations.

### Eight delay bytes

Incrementing a low byte changes the relevant emulated delay by 4,206 ticks;
incrementing a high byte changes it by 1,076,738 ticks. These are CPU-model
ticks, not a measured wall-clock calibration.

| Physical ROM | Tested influence | Likely panel timing field |
| --- | --- | --- |
| `1113` | Startup | T2, one byte |
| `1114:1115` | Startup, big-endian pair | T3 |
| `1116` | Shutdown | T4, one byte |
| `1117:1118` | Shutdown, big-endian pair | T5 |
| `1119:111a` | Shutdown/restart wait, big-endian pair | T7 |

The firmware passes twice the sum of the first two fields to its busy wait at
startup, twice the next two on shutdown, then twice the final field. The T2/T3/
T4/T5/T7 names are inferred from ordering and the vendor's short/long timing
ranges. The busy-wait unit and physical pin timings are not calibrated; the
factor of two does not by itself establish milliseconds. See section 4.7 of the
[CS5211 datasheet](https://datasheet4u.com/pdf-down/C/S/5/CS5211-CapStone.pdf).
Two high-byte mutations initially exceeded the 20-million-tick test budget;
both completed with 100 million. A high bit can also wrap the 16-bit software
delay calculation. These bytes are poor candidates for blind colour trials.

## 4. Recovery and status handling

Clearing `000c` bit 5 or invalidating `0611` after startup causes writes
`01d8=b4`, then `94`, and clearing `00e1` bit 7. Restoring status re-enters
clock calculation and copies the profile registers again.

Changing the M/N inputs while keeping the tested ready statuses asserted does
not update the clock registers in the steady loop. The same change is applied
after recovery. Real hardware may independently detect a clock change; that
behaviour is outside the experiment.

Changing `00ca` from 0 to 15 after startup did not select profile 15 during
recovery: IRAM[08] remained zero. Cold-start tests of all 256 GPIO byte values
with uniquely marked profiles confirmed selection from the low four bits.

The lane-status predicate requires exact `0611=07` for `(060b & 1f)==1`,
otherwise exact `77`. Enhanced-framing high bits in `060b` are masked. Extra
bits in `0611` cause rejection in the isolated predicate tests. At PC `03e4`,
the read of `0613` is ORed with 1 immediately before JNZ, so it cannot make that
branch false. Calling this an interlane-alignment bug would require establishing
the undocumented register's semantics first.

A changed `01b4` marker invokes a separate recovery routine, writes a fixed
register set, restores `01b4=5c`, and increments `00c4`. This path is distinct
from normal loss-of-ready handling.

## Recommended next colour experiment

1. Keep power timings, clock-source settings, and profile[0] fixed initially.
2. Use the existing exact-code diagnostic PNGs to distinguish modulo-64
   truncation from channel/bit permutations, source transforms, and odd/even
   faults. A matching simulation alone does not uniquely establish the cause.
3. For hardware register trials, log the chosen profile, actual source format,
   firmware hash, readback, and image result. Check for link retraining and
   reapplication of the original profile. If only EEPROM trials are possible,
   ensure the intended selected profile is actually patched.
4. Test only effective output changes from the map above; track `01f4`'s two
   configuration sources together. A colour outcome is the oracle, not boot
   completion or an image merely appearing.
5. Retain the opaque pre-code blocks as a separate unresolved lead. Neither
   emulator can establish their hardware role.

## Reproduce and inspect

```sh
python3 scripts/cs5211_blackbox.py --build
python3 scripts/cs5211_campaign.py
python3 scripts/cs5211_crosscheck.py
```

Requires Python 3, clang, the pinned `tools/emu8051` checkout, and `s51` from
SDCC for the independent check. The build path currently targets macOS.

- `scripts/cs5211_campaign.py`: explicit inputs and experimental assertions.
- `artifacts/cs5211-blackbox/mutations.json`: per-bit register/control-flow changes.
- `clock-boundaries.json`, `clock-fuzz.json`, `crosscheck.json`: arithmetic evidence.
- `runtime-buttons.json`, `power-delays.json`, `power-button.json`: control tests.
- `link-recovery.json`, `status-predicate.json`: state-machine experiments.
- `invalid-clock-inputs.json`: fault-injection outcomes.
- `ucsim-*.txt`: independent emulator transcripts.
- `ghidra-listing.txt`: listing with evidence-supported function names.

No firmware was flashed. No LVDS waveform or actual panel image was produced by
these emulators. The experiments narrow the firmware map without claiming a
verified colour fix.
